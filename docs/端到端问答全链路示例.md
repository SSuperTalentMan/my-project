# 商枢 CommercePivot · 一次问答的端到端全链路示例

> 本文是**真实运行记录**，不是设计说明。所有数字、结论、耗时都来自 2026-09-14 本机实际运行：
> MySQL + Redis + Milvus Lite 全部在线，大模型真实调用百炼 `qwen3.7-flash`，未使用任何 mock。
>
> 主线问句：**「上个月抖店退货率最高的商品是什么」**（架构文档 §7 的示例问句）
> 复现命令见文末 §7。

---

## 1. 总览：一次请求走过了什么

| # | 阶段 | 组件 | 主线实测 |
|---|------|------|----------|
| 1 | 请求进入 | FastAPI + 中间件 | `POST /api/v1/chat/ask` → HTTP 200 |
| 2 | 鉴权 | JWT HS256（标准库手写） | `role=operator`，`principal.can("chat")` 通过 |
| 3 | 限流 | Redis 固定窗口 | 未触发（`RATE_LIMIT=60/min`） |
| 4 | 缓存 | Redis `cache:ask:{skill}:{role}:{hash}` | `use_cache=false`，主动跳过 |
| 5 | 意图识别 | `intent_node` | `after_sales` 置信度 **0.8333** |
| 6 | 槽位抽取 | `slot_node` | `platform=抖店`、`2026-08-01~08-31`、`metric=退货率`、`top_k=5` |
| 7 | 条件路由 | `route_after_slot` | `plan`（槽位齐，非闲聊） |
| 8 | 计划编排 | `planning_node` | 收敛为 **1 个** Agent：`order_analysis_agent` |
| 9 | A2A 调度 | `a2a_route_node` + registry | `completed`，**102 ms** |
| 10 | MCP 取数 | 2 次工具调用 | `query_orders` + `query_after_sales` |
| 11 | 聚合 | `aggregate_node` | 表格 5 行 × 7 列 |
| 12 | 回答生成 | `answer_node` → qwen3.7-flash | **2696 ms**，931 tokens |
| 13 | 落库与返回 | MySQL + Redis | 会话写入，返回 JSON |

**总计 2819 ms，编排模式 `langgraph`，无任何降级。**

## 2. 主线：逐步拆解

### Step 1｜请求进入接入层

**做什么**：前端/客户端把用户问句 POST 到接入层，带上 JWT。

**技术点**
- `AskRequest` 用 Pydantic 校验：`extra="forbid"` 拒绝多余字段，`question` 限 1~1000 字。
- 中间件 `RequestContextMiddleware` 为每个请求生成 32 位十六进制 `X-Request-ID`，写入 `contextvars`，之后 MCP / A2A / LLM 各层只读即可，日志与审计统一带上它。
- 路径做归一化（`/chat/sessions/{id}`）再打 Prometheus 标签，避免动态段导致标签基数爆炸。

**代码位置**：`api/schemas.py:10`、`main.py` 的 `RequestContextMiddleware`、`core/context.py`

**真实请求**
```json
POST /api/v1/chat/ask
Authorization: Bearer <jwt, 209 chars>
{ "question": "上个月抖店退货率最高的商品是什么",
  "include_trace": true, "use_cache": false }
```

---

### Step 2｜鉴权与角色权限

**做什么**：解出「谁在问、能不能问」。

**技术点**
- JWT 用 `hmac + hashlib + base64` 手写实现 HS256，**不引入 PyJWT**，签名比对用 `hmac.compare_digest` 防时序攻击。
- 权限矩阵集中在 `ROLE_PERMISSIONS`：`admin=["*"]`、`operator=["chat","mcp","mcp:read","a2a","report","ticket"]`、`customer=["chat"]`。
- 越权不返回 500 而是明确的 `ForbiddenError`（错误映射统一在 `api/errors.py`）。

**代码位置**：`core/security.py:49`（签发）、`:76`（校验）、`:141`（`require` 依赖工厂）

**真实观测**：以 `subject=demo-analyst, role=operator` 签发令牌，`principal.can("chat")` 为真。

---

### Step 3｜限流（Redis 固定窗口）

**做什么**：同一 IP + 同一路径按分钟计数，超限返回 429 + `Retry-After`。

**技术点**
- `key = rate_limit:{ip}:{path}:{window}`，首次 `incr` 后 `expire 120s`。
- **Redis 不可用时 fail-open（放行）**，而不是把整站打死 —— 限流是保护措施，不该成为新的故障点。

**代码位置**：`core/security.py:163` `RateLimiter`、`:193` `rate_limit_dependency`

---

### Step 4｜问答缓存

**做什么**：命中就直接返回，不跑整条链路。

**技术点**
- 缓存键带**意图维度**：`cache:ask:{skill}:{role}:{sha256(question)[:32]}`。
- 因为 `skill` 来自意图识别，所以在入口先做一次**轻量意图分类**来构造键（规则分支微秒级），否则键拼不出来。
- **降级结果不回写缓存**（`if not result.get("degraded")`），避免把一次失败固化成一小时的错误答案。

**代码位置**：`api/chat.py:158-183`、`db/redis.py:186` `cache_key`

**真实观测**：本次 `use_cache=false`，走 `CACHE_CALLS{result=bypass}`。

---

### Step 5｜意图识别 `intent_node`

**做什么**：把自然语言映射到业务意图，并给出**可解释**的依据。

**技术点**
- **两级意图体系**：一级业务域（经营分析 / 知识问答 / 报表 / 工单 / 闲聊），二级分析主题（订单 / 商品 / 售后 / 销售 / 库存 / 广告）。一个意图对应一个执行 Agent，这张表就是「意图 → Agent」的路由真相。
- **规则优先 + BERT 可选融合**：关键词带权重 + 正则强规则先出分，`score/(score+4)` 归一化避免长问句被无限放大；配了 `INTENT_BERT_PATH` 时按标签取 BERT 分，与规则**取更自信的一方**（`max`），而非加权平均 —— 避免任一单点误判拖低整体。
- **`_post_process` 的五条歧义消解规则**是这一层的真正价值：
  1. 规则询问优先于命中业务词（「生鲜支持七天无理由退货吗」→ 知识问答，不是售后统计表）
  2. 分析型信号压制知识问答
  3. 「退货/退款」语境下售后优先于订单
  4. 报表作为附加动作，不与业务意图争主位
  5. 无关键词但短问句 → 知识问答兜底

**代码位置**：`models/intent_bert.py:33`（意图表）、`:217`（打分）、`:360`（后处理）

**真实观测**（这句为什么被判成售后分析）
```json
{"primary": "after_sales", "primary_name": "售后分析", "confidence": 0.8333, "source": "rule",
 "scores": {"after_sales": 0.8333, "product": 0.5, "knowledge_qa": 0.3333},
 "hits": {"after_sales": ["退货率", "退货", "re:退货率|退款率|售后率|退款占比",
                          "re:退(货|款).*(最多|最高|排名|top)"],
          "product": ["商品"]},
 "matched": ["after_sales", "product"],
 "agents": ["after_sales_agent", "product_analysis_agent"]}
```
注意 `matched` 里有 **两个**意图（售后 + 商品），`agents` 也列了两个 Agent —— 如果规划层照单全收，就会多打一次无关的商品分析。这正是 Step 8 存在的理由。

---

### Step 6｜槽位抽取 `slot_node`

**做什么**：把「上个月」「抖店」这类说法转成结构化参数。

**技术点**
- **刻意不调 LLM**：平台、指标、状态的值域是**封闭的**，规则比模型更准、零成本、可回归测试。
- 时间走 `utils/timeparse.parse_period`，支持「上个月 / 近7天 / 昨天」等口语，输出 ISO 区间 + 人类可读 label。
- **缺槽位只追问「缺了会答错」的**：`REQUIRED_SLOTS` 对经营分析类全部为空 —— 没给时间就默认近 30 天并在答案里注明口径，而不是弹一句反问把用户烦死。真正必须的（排行类缺 `metric`）才追问。
- **广告渠道词先于店铺平台判定**：「京东京准」含「京东」、「巨量引擎」口语简称「巨量」，顺序错了就会把广告数据按店铺平台过滤。

**代码位置**：`orchestrator/slots.py:242`（主入口）、`:397`（缺失判定）

**真实观测**
```json
{"platform": "抖店", "start_date": "2026-08-01", "end_date": "2026-08-31",
 "period_label": "2026年8月", "metric": "退货率", "top_k": 5,
 "order": "desc", "after_sale_type": "退货"}
```
`missing_slots: []`、`defaults_applied: []` —— 槽位齐、没套默认值，所以答案里不需要加「数据说明」。

---

### Step 7｜条件路由 `route_after_slot`

**做什么**：三条分支的岔路口。

```
闲聊（主意图=闲聊 且 没有任何业务 Agent 被命中） → answer_node（寒暄直答）
有 clarification 且缺关键槽位                      → answer_node（模板追问）
其余                                              → planning_node（正常分析）
```

**技术点**：闲聊判定的硬前提是**没有任何业务意图命中**。「你好，帮我看下上个月销售额」必须保留 `sales` 正常走分析，不能因为开头是「你好」就当成客套话丢掉。

**代码位置**：`orchestrator/nodes.py:142` `_is_smalltalk`、`:155` `route_after_slot`

**真实观测**：本句走到 `plan`。

---

### Step 8｜计划编排 `planning_node`（含金量最高的一步）

**做什么**：决定到底调哪几个 Agent。核心动作是**去重与收敛**，不是简单叠加。

**技术点**
- 主意图对应的 Agent 作为 `primary`，`matched` 里的次要意图作为 `secondary`。
- **政策/规则类知识问答的唯一执行者**是 `knowledge_rag_agent`：问句里出现「退货」会让意图引擎顺带命中 `after_sales`，但用户要的是**解释**而不是**退货数据**，此时拉业务 Agent 只会把无关流水灌进表格。判据是「有没有明确的取数诉求」（`_asks_for_data`）。
- **退货率排行口径收敛**：退货率是「订单量 × 退货单数」的联合口径，唯一执行者是 `order_analysis_agent`；此时把仅因问句出现「商品」二字而命中的 `product_analysis_agent` 剔除，避免同一口径被两个 Agent 重复计算。
- 同一 Agent 只调一次（`deduped`），多意图合并到主次角色里。

**代码位置**：`orchestrator/nodes.py:165` `planning_node`、`:321` `_DATA_ASK_HINTS`、`:328` `_asks_for_data`

**真实观测**（意图层命中 2 个 Agent，规划层收敛为 1 个）
```json
"plan": [{"agent": "order_analysis_agent", "intent": "after_sales",
          "focus": "return_rate", "role": "primary"}]
"plan_reason": "售后分析 → order_analysis_agent；命中退货率排行口径 → 收敛为
                order_analysis_agent(focus=return_rate)，避免仅因问句出现「商品」
                二字就并行调用无关 Agent 污染结论"
```
> ✅ 说明文案里的「售后分析」直接取自计划项自身的 `intent`。早期版本用「Agent 名反查意图表」，而 `sales`/`order`/`ad` 三个意图共用 `order_analysis_agent`（`after_sales` 不在其中，它有自己的 `after_sales_agent`），反查按字典序命中最前的 `sales`，把这里写成「销售分析」（见 §6 修复 1）。

### Step 9｜A2A 并行调度 `a2a_route_node`

**做什么**：把计划派发给子 Agent，并拿到带状态的任务记录。

**技术点**
- `registry.dispatch_many` 用 `asyncio.gather` 并行唤起多个 Agent，**单点失败不影响其他 Agent**：超时/熔断/异常都会产出一条 `status=failed` 的记录，交给聚合层决定怎么呈现（§11「返回部分结果」）。
- `BaseAgent.run` 是标准任务状态机：`submitted → working → completed | failed | canceled`，状态落库到 `agent_tasks` 表。
- **稳定性护栏**：`asyncio.wait_for(timeout=a2a_timeout_s)` 单任务超时 + `CircuitBreaker` 连续失败 3 次熔断 30 秒（冷却后进 half-open 试探）。
- **分层约束**：子 Agent 取数一律走 `self.call_tool()` 进 MCP 工具层，**Agent 不直连数据库**。

**代码位置**：`agents/base.py:222` `BaseAgent`、`:144` `CircuitBreaker`、`agents/registry.py:133` `dispatch_many`

**真实观测**
```json
[{"id": "order_analysis_agent-99ee8fe9b237", "status": "completed",
  "error": null, "elapsed_ms": 102}]
```

### Step 10｜MCP 工具取数（两次调用 + Agent 内 join）

**做什么**：退货率不是一个现成的 SQL 聚合，而是**分两步取数、在 Agent 内算比率**。

**技术点**
- **工具层职责**：`ToolRegistry.call` 统一做参数校验（Pydantic → JSON Schema）、同步 handler 走 `asyncio.to_thread` 不阻塞事件循环、`wait_for` 超时、失败重试 1 次、**审计落 JSONL + MySQL 且参数脱敏**、写操作受 `ENABLE_WRITE_OPS` 门禁（默认只读）。
- **`call()` 不抛异常**，返回结构化 `ToolResult{ok, code, message, data, summary, rows}` —— 这样上层 Agent 能自己决定是否降级，也天然满足「仍失败返回错误码」。
- **口径拆分**：`query_orders(breakdowns=['product'])` 拿每个商品的订单量；`query_after_sales(after_sale_type='退货', breakdowns=['product'])` 拿每个商品的退货单数。
- **Agent 内 join 的两个坑**（都在代码注释里留了痕）：
  - 工具侧的 product 切片是按 `(product_id, platform)` 分组的，必须**按商品累加**而不是按 key 直接覆盖 —— 早期版本覆盖导致全平台口径下同一商品多平台行互相顶掉，表现为「全平台退货率 0%」。
  - **样本量下限**：默认要求至少成交 5 单才进排行，避免「1/2 = 50%」这种低基数比率给出误导性结论。

**代码位置**：`mcp_server/registry.py:151` `call`、`mcp_server/tools/order_tools.py:68`、`agents/order_agent.py:77` `_return_rate`

**真实观测**（`source_tools: ["query_orders","query_after_sales"]`）
```json
{"overall_return_rate": 3.66, "order_count": 382, "return_count": 14,
 "product_count": 32, "min_orders": 5,
 "top_product": "折叠晾衣架", "top_return_rate": 33.33}
```

### Step 11｜聚合 `aggregate_node`

**做什么**：把多个 Agent 的输出合成统一的「结论 + 指标 + 来源 + 表格」。

**技术点**
- 按 `AGENT_PRIORITY` 排序（报表/分析排在知识问答之前），保证多 Agent 时结论顺序稳定。
- `metrics` 加 Agent 前缀（`order_overall_return_rate`）避免不同 Agent 的同名指标互相覆盖。
- `_build_table` 用**列偏好表**决定前端展示哪些列，列名走 `COLUMN_LABELS` 中文化；最多 50 行并标 `truncated`。
- 任一 Agent 未完成都会置 `degraded=True` 并记 `degrade_reasons`，最终由回答层如实交代「部分结果」。

**代码位置**：`orchestrator/nodes.py:374` `aggregate_node`、`:450` `_build_table`、`:45` `TABLE_COLUMNS`

**真实观测**（5 行 × 7 列）

| 折叠晾衣架 | 家居 | 抖店 | 6 | 2 | 33.33 | 311.21 |
| 阳澄湖大闸蟹礼券 | 食品 | 抖店 | 8 | 2 | 25.0 | 2734.86 |

### Step 12｜回答生成 `answer_node`

**做什么**：把结构化结果写成一段人话。

**技术点**
- **提示词约束比模型能力更重要**：系统提示明确「只依据给定的查询结果作答，不得编造数字」「结论先行」「分组结果必须逐行完整列举，行数超过 8 行才可归纳但要说明共 N 行」「纯文字不要 Markdown 表格（表格由前端单独渲染）」。
- **`enable_thinking=false`**：qwen3.7-flash 是混合推理模型，默认会先生成思维链（实测 2447 字 / 839 token），关掉后省约 2.8 倍 token 且快 8 倍。只在「要关」时显式下发该字段，换成不支持它的模型也不会 400。
- **降级不编数字**：LLM 不可用（未配 `API_KEY`、额度耗尽、鉴权失败）时**不用模型编，改用已查到的真实数据拼模板回答** ——「宁可用模板说清事实，也不用模型编数字」。
- **错误码分层提示**：同一句「HTTP 403」背后可能是密钥失效 / 免费额度耗尽 / 模型未开通，`_PROVIDER_HINTS` 把处置方式直接写进错误文案。
- `answer_source`（走了哪条链路：`llm`/`template`/`clarification`/`chitchat`）与 `answer_meta.generator`（这段字是谁写的）是**两个正交维度**，分开记录才不会互相遮住。

**代码位置**：`orchestrator/nodes.py:470`（提示词）、`:673` `answer_node`、`models/llm_client.py:142` `_payload`

**真实观测**
```json
{"answer_source": "llm",
 "answer_meta": {"model": "qwen3.7-flash",
   "usage": {"prompt_tokens": 708, "completion_tokens": 223, "total_tokens": 931},
   "llm_elapsed_ms": 2695, "generator": "llm"}}
```
```

2. 阳澄湖大闸蟹礼券（食品），订单量8单，退货2单，退货率 25.00%，退款金额 ¥2,734.86；
```

### Step 13｜落库与返回

**做什么**：会话写入，答复返回。

**技术点**
- MySQL `chat_messages` 存问答对 + Redis 存会话上下文（近 20 轮、TTL 1 小时），两条都失败也**不影响回答**（`_persist_turn` 整体 try/except）。
- 非降级结果的回答**回写缓存**。
- 返回体包含 `intent / slots / plan / plan_reason / agent_tasks / table / findings / metrics / citations / notes / node_timings / answer_meta` —— 前端可以逐步渲染「意图卡片 → 规划 → 表格 → 回答」。

**代码位置**：`api/chat.py:108` `_persist_turn`、`:196-205`

## 3. 三条分支的差异（同一套编排，不同的路）

### 3.1 知识问答（RAG）：「七天无理由退货的条件是什么」

走得最远的一条链路 —— 多了向量检索与重排。

| 环节 | 结果 |
|------|------|
| 意图 | `knowledge_qa` **0.78**（规则 0 生效：出现「条件」类措辞且无取数诉求，压掉因「退货」命中的 `after_sales` 到 0.3） |
| 槽位 | **只有** `knowledge_query`，业务槽位（平台/时间/指标）全部不填 —— 避免给政策咨询挂上「近 30 天 / 全平台」的误导性统计口径 |
| 计划 | 仅 `knowledge_rag_agent`，`plan_reason`: 「政策/规则咨询只检索知识库，不叠加业务数据」 |
| 工具 | `search_knowledge` → `retrieval.service`：**BGE-M3 稠密+稀疏 → Milvus hybrid 召回 → BGE-Reranker 精排** |
| 溯源 | 3 条 citations：`faq-001` 0.7391 / `faq-023` 0.5402 / `faq-017` 0.3955，均标 `retrieval_mode: milvus-hybrid` |
| 耗时 | **9287 ms**，其中 `a2a_route_node` 7557 ms（首次加载 embedding + 重排模型的冷启动）、`answer_node` 1723 ms |

**关键点**：向量检索**没有降级**，走的是真实混合检索 + 重排。若 Milvus 不可用会自动降级 MySQL 全文/LIKE，并在 `notes` 里如实标注 `retrieval_mode`。

**回答**：正确给出「自签收次日起 7 个自然日内、商品保持完好」，并列出不支持无理由退货的商品类型，全部来自知识库原文。

### 3.2 闲聊短路：「你好」

|------|------|

## 4. 这条链路体现的工程约束

| 约束 | 落地方式 |
|------|----------|
| **分层** | 接入 / 编排 / Agent / 工具 / 模型五层，**Agent 不直连 DB**，取数一律过 MCP 工具层 |
| **可解释** | 意图给 `scores`+`hits`（命中哪些词）、规划给 `plan_reason`、检索给 `citations`+`retrieval_mode`、耗时给 `node_timings`、生成给 `answer_meta` |
| **确定性优先** | 封闭值域（平台/指标/状态）用规则不调 LLM；时间口语用 `timeparse`；模板回答保证「不编数字」 |
| **多档降级** | LangGraph 编译失败 → 顺序执行；LLM 不可用 → 模板回答；Milvus 不可用 → MySQL 全文/LIKE；Redis 不可用 → 缓存/限流 fail-open；MySQL 不可用 → 返回降级标记而非 500 |
| **稳定性护栏** | 工具超时 + 重试 1 次、Agent 超时 + 熔断、限流固定窗口、写操作默认只读 |
| **可观测** | X-Request-ID 贯穿、审计 JSONL + MySQL、Prometheus 指标、`/metrics` `/status` |

## 6. 真实运行中发现的三处瑕疵（已全部修复）

这三处都是「跑真实链路」才暴露的，属于 **可解释性与回答完整度** 问题（不影响正确性）。三处均已修复，并各自补了一条 `smoke` 回归断言防复发 —— 自检从 13 项增至 **16 项**。

### 修复 1｜`plan_reason` 把「售后分析」写成「销售分析」

- **现象**：`plan_reason` 输出「**销售分析** → order_analysis_agent」，但本句意图是 `after_sales`（售后分析）。
- **根因**：`planning_node` 重写说明文案时，用「Agent 名 → 意图名」**反查**（`next((k for k,v in INTENT_TAXONOMY.items() if v["agent"]==item["agent"]), "")`）。而 `sales` / `order` / `ad` **三个意图都映射到同一个 `order_analysis_agent`** —— 注意 `after_sales` 并不在其中（它有自己的 `after_sales_agent`），但退货率排行这个计划项被规划规则收敛到了 `order_analysis_agent`，`intent` 仍是 `after_sales`。反查按字典遍历顺序命中排最前的 `sales`，于是「售后分析」被显示成「销售分析」。
- **修复**：不再反查，直接用计划项里已经存在的 `item["intent"]` ——
  `name = (INTENT_TAXONOMY.get(item.get("intent") or "") or {}).get("name") or item["agent"]`
- **代码位置**：`orchestrator/nodes.py` `planning_node`（退货率收敛分支的 `final_desc` 构造）
- **验证**：`plan_reason` 现为「**售后分析** → order_analysis_agent；命中退货率排行口径 → 收敛为 …」；对照场景「上个月各平台的销售额分别是多少」仍正确显示「销售分析 → order_analysis_agent」（那里的 intent 确实是 `sales`，说明修的是反查、不是硬编码）。

### 修复 2｜LLM 回答出现「订单量未显示」

- **现象**：退货率排行场景，模型对第 2~5 名输出「订单量未显示，退货单数未显示」；而同样模型在「各平台销售额」场景却逐行给了订单量和 GMV。
- **根因**：`_context_for_llm` 只把 `findings` 文本喂给模型，**没把 `table.rows` 的明细行喂进去**。两条链路的 `findings` 信息密度不同：`_order_findings` 每个平台拼了「X 单 / ¥Y」；而 `_return_findings` 只给了「商品名（退货率%）」，**没给单量** —— 模型只能诚实地说「未显示」。
- **修复**：`_context_for_llm` 增加一段表格逐行明细（`_render_table_for_llm`，列名走 `COLUMN_LABELS` 中文化，上限 `MAX_CONTEXT_ROWS = 30` 行，超出则注明「仅列前 N 行」）。
- **代码位置**：`orchestrator/nodes.py` `_context_for_llm` / `_render_table_for_llm`
- **验证**：同问句下模型逐行给出「订单量6单，退货2单，退货率33.33%，退款金额¥311.21」等完整明细；`smoke` 断言「LLM 上下文含表格明细」PASS（实测表格 5 行、上下文 1027 字、首行已在上下文）。

### 修复 3｜`include_trace` 返回的 trace 不全

- **现象**：请求 `include_trace=true`，返回的 `trace` 只有 2 条：`{"stage":"llm"}` 与 `{"stage":"node","node":"answer_node"}`；而 `node_timings` 是完整的 6 个节点。
- **根因**：trace 用 `contextvars` 累积，但 **LangGraph 的节点在各自的隔离子上下文中执行**（工具调用还额外经过 `asyncio.to_thread`）。当时的实现是 `_trace.set(_trace.get() + (item,))` —— `set()` 只改当前上下文里的绑定，**子上下文换出去的新对象不会回传给父上下文**，于是最终 state 只拿到 `answer_node` 自己上下文里的那两条。
- **修复**：把 trace 从「不可变元组 + `set()`」改成「**可变列表 + 原地 `append`**」（`core/context.py`）。入口（HTTP 中间件 / `request_context` / 编排器 `ainvoke`·`astream`）用 `begin_trace()`/`ensure_trace()` 创建一个**新列表**，之后所有子上下文持有的是**同一个列表引用**，任何深度的追加都能被最外层读到。
  - 相比「每个节点把 trace 片段随 state 返回」的方案，这个改法不动任何节点函数签名，且**天然覆盖 `asyncio.to_thread` 里的 MCP 调用**（线程池同样共享该引用）——实测 `mcp` 阶段就能进来。
  - 跨请求隔离由「入口每请求新建列表」保证：默认值刻意用 `None` 而不是模块级空列表，避免未显式开启 trace 的上下文共享全局对象。
- **代码位置**：`core/context.py:begin_trace/ensure_trace/trace_add/get_trace`、`main.py:RequestContextMiddleware`、`orchestrator/graph.py:ainvoke/astream`
- **验证**：同问句的 `trace` 从 2 条变为 **15 条**，覆盖全链路 8 类阶段 ——
  `intent → node(intent) → node(slot) → plan → node(planning) → a2a-dispatch → agent-tool(query_orders) → mcp(query_orders) → agent-tool(query_after_sales) → mcp(query_after_sales) → a2a(order_analysis_agent) → node(a2a_route) → node(aggregate) → llm → node(answer)`。
  HTTP 路径（真实 `curl` 经中间件）与进程内路径（CLI）结果一致。

### 回归防线

三处修复各配一条断言，随 `smoke` 一起跑（证据全部取自同一次真实 e2e 的 state，不额外起链路）：

| 断言 | 判定 |
|------|------|
| `规划说明·意图名口径` | `plan_reason` 含「售后分析」且**不含**「销售分析」 |
| `链路 trace 完整性` | `len(trace) > 2` 且阶段集合含 `{node, a2a-dispatch}` |
| `LLM 上下文含表格明细` | 上下文含「逐行明细」且首行商品名已进入上下文 |

> 用 `python -m commercepivot smoke` 一次跑完；`FAIL` 会以非零码退出，可直接接 CI。

## 7. 一句话总结

> 一次问答 = **接入层兜住安全与成本** → **编排层把自然语言收敛成确定的执行计划** → **Agent 层并行调度并守住分层约束** → **工具层做校验、审计与降级** → **模型层只负责把真实数据说成人话**。
> 每一层都能单独降级、单独观测、单独解释，这就是这条链路能上生产的原因。
